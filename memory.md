### 2026-08-06 — Start-Dev.bat actually didn't work at all; found and fixed 2 real cmd.exe parser bugs

User reported Start-Dev.bat "does nothing visible" when run — no windows, no servers, nothing reachable — directly contradicting the prior session's claim that its constituent commands were validated (true, but the *whole script* had never actually been run end-to-end, and that gap mattered). Debugged for real per the user's explicit instructions (run directly, capture real output, don't assume) rather than re-reading the script and declaring it correct.

**Root cause, found by isolating the script piece by piece with `Start-Process -RedirectStandardOutput/-RedirectStandardError` and reading the actual bytes**: two lines had **unescaped literal parentheses inside multi-line `if (...)`/`if (...) else (...)` blocks**, which cmd.exe's block parser treats as a premature end-of-block marker — everything after that stray `)` (including `pause`/`exit /b 1`, which were meant to be conditional) gets pulled outside the block and executed **unconditionally**, every single run, regardless of the actual if-condition:
- `Start-Dev.bat`: `echo ... (from server\node_server, with DATABASE_URL pointed at it)` inside the mysql-container-check block — meant this script has **always** stopped dead with an unconditional `pause`+`exit /b 1` immediately after "Ensuring engirent-mysql-dev container is running...", regardless of whether Docker/the container were actually fine, and **before ever reaching any of the 6 `start "..." cmd /k ...` lines**. This is the exact, complete explanation for the user's report — the script exits before any service window ever opens.
- `Start.bat`: the same pattern, `echo ... issue(s) and re-run...` inside the final summary's `else` block.

Reproduced both in complete isolation (a minimal repro with an always-false `if` condition still ran the `pause`/`exit` inside it, proving the block boundary itself was broken, not the condition logic) before touching the real files — then fixed both by escaping the parens (`^(...^)`), matching the pattern already correctly used elsewhere in both scripts. Found a **second**, narrower bug the same way: `call :wait_for_http "Kiosk UI (mocked)" ...` — parens inside a quoted argument to `call`, on a bare single-line `if` with no wrapping block — also broke the parser (empirically confirmed parens-in-quotes are safe inside `start "title (...)" ...` within a real block, but not in this specific `call` pattern); fixed by dropping the parens from that one label string.

**Verified the fix is real, not just theorized**: killed all locally-running dev services, ran the fully-fixed `Start-Dev.bat` completely fresh via `Start-Process` with real file-redirected output (avoiding the earlier discovery that piped/captured output can hang indefinitely if a spawned `cmd /k` window inherits the pipe handle — `cmd /k` never exits, so the pipe never sees EOF). Confirmed via independent means, not just the script's own self-report: all 6 `start`-ed windows exist as real, distinct processes; all 6 target ports are listening; `curl` returns correct real content from each service; the script's own Components Check reports **all 7 items [OK]** and prints "All checks passed"; and — the check the user explicitly asked for — Playwright screenshots confirm the Admin Console, Public Site, and Phone App (Flutter web) all render correctly in an actual browser at their real URLs.

**Also learned, worth remembering**: my own automated invocation of `.bat` files that use `start "title" cmd /k ...` is unreliable to test naively — capturing output via inherited pipe handles can hang forever (the spawned window never closes, so the pipe never EOFs), and even file-based redirection without an explicit interactive stdin occasionally trips an unrelated `for /f 'curl ...'` subshell quirk ("Input redirection is not supported") that a real user's normal double-click / interactive terminal would never hit. Neither of those is a bug in the scripts — only the two escaped-parenthesis fixes above are.
