## Runbook — desktop-gklhcri comes back from a reboot with EngiRent down (recurring, accepted tradeoff)

**Symptom**: MySQL (port 3307) is up but ports 5000 (Node API), 3001 (Admin Console), 3000 (`client/web`), 8092 (Flutter web) are not listening. `docker`/DB survives a reboot independently; the app services don't.

**Root cause, confirmed 2026-09-03, won't change until someone re-registers the tasks**: all seven `EngiRent*` Scheduled Tasks (`EngiRentNode`, `EngiRentMl`, `EngiRentAdmin`, `EngiRentWeb`, `EngiRentTunnelAPI`, `EngiRentTunnelAdmin`, `EngiRentTunnelWeb`) run as `transfer` with Logon Type **Interactive**, which cannot fire an `ONSTART` trigger — no interactive session exists at boot. **The user has explicitly chosen not to fix this registration** (would need `/RU SYSTEM`, which Claude Code's auto-mode classifier blocks outright over SSH) — the accepted workflow is: notice it's down, start everything back up by hand. This will keep happening on every reboot until someone re-registers the tasks as `SYSTEM` (or does it manually via Task Scheduler's GUI, which isn't gated the way an automated `schtasks /Create` is).

**The fix, every time — `Start-ScheduledTask` is NOT blocked, only `/Create`/`Set-ScheduledTask` (registration changes) are**:
```powershell
foreach ($t in 'EngiRentNode','EngiRentMl','EngiRentAdmin','EngiRentWeb','EngiRentTunnelAPI','EngiRentTunnelAdmin','EngiRentTunnelWeb') {
  Start-ScheduledTask -TaskName $t
}
```
Run over SSH as `transfer@desktop-gklhcri`. Services take **30-60+ seconds** to actually bind their ports after the task shows `Running` (Next.js compile/start time, the ML service's model load) — don't conclude it failed from an empty port check taken immediately after firing the tasks. Verify with:
```powershell
Get-NetTCPConnection -LocalPort 5000,3001,3000,8092 -State Listen -ErrorAction SilentlyContinue
```
all four should show up once fully started. Then check the tunnels resolve from the public internet, not just the tailnet (the Cloudflare quick-tunnel hostname rotates on every process restart — same accepted tradeoff as EcoCharge's).

**How to apply:** if a session finds EngiRent's ports down, don't assume the deployment is broken — check whether it's just this recurring reboot-survival gap first (compare against this runbook), run the `Start-ScheduledTask` loop above, wait a full minute, then re-verify before escalating it as a new problem.

**Two real things found doing this restart for real, 2026-09-03, worth fixing separately from the registration issue:**
1. **`svc-admin.bat` and `svc-web.bat` run a full `next build` on every single restart, not `next start` against a pre-built `.next`.** Confirmed from the actual logs (`admin3.log`, `web3.log`): Admin's build alone took 2.6 minutes before even reaching `next start`; Web's build hit repeated `ECONNRESET`/`socket hang up` errors (retried and eventually succeeded, but that's genuine network flakiness during a step that shouldn't need the network at all). This means every reboot-recovery costs several minutes of extra downtime beyond just restarting a process, and carries a real risk of the build itself failing. The right fix is a `.bat` that runs `next start` against an already-built app, with `next build` happening once as part of an actual deploy step — not verified/changed this session, flagging for a future one.
2. **There is no Scheduled Task for the Flutter web surface (port 8092) at all** — confirmed via a full `Get-ScheduledTask` listing on the host; only the 7 tasks above exist. Either it's no longer part of the live deployment (plausible — v1.7.0 shipped a real signed APK, so the browser-based Flutter build may have been superseded) or it was simply never automated. Not resolved this session — don't assume port 8092 should be up without checking which of the two this actually is first.

**Third real thing found, same restart, worth its own callout: `Stop-ScheduledTask` does not actually kill the underlying `node`/`cmd` process.** After editing `.env` and running `Stop-ScheduledTask -TaskName EngiRentNode` then `Start-ScheduledTask`, the exact same PID stayed bound to port 5000 — the old process, still running with the pre-edit environment, never actually stopped. The task's `State` still reports `Ready`→`Running` normally, giving no visible sign anything's wrong. **The real fix: `Stop-Process -Id <pid> -Force` on the actual owning process (from `(Get-NetTCPConnection -LocalPort <port> -State Listen).OwningProcess`) before `Start-ScheduledTask`, every time an `.env` or code change needs picking up** — a plain `Stop-ScheduledTask`/`Start-ScheduledTask` cycle is not sufficient and will silently keep serving the old config. Confirmed by re-running the same E2E suite: failed identically twice against the "restarted" API, passed clean the moment the real process was killed.

**Second real bug found and fixed the same session: `API_PUBLIC_URL`, `CLIENT_WEB_URL`, and `CLIENT_ADMIN_URL` in `.env` were all stale**, pointing at dead tunnel hostnames from a prior restart, not the fresh ones this restart generated — found because `e2e-listing-video.mjs` failed trying to fetch a media URL the API itself had just returned (`getaddrinfo ENOTFOUND` on the old hostname). This is the exact "a rotated hostname breaks every consumer, and the API's own outbound-URL config is itself a consumer" risk this file already knew about in the abstract; this is the first time it was caught live, mid-test, rather than assumed fixed. Fixed by editing `.env` directly (blocked once by the auto-mode classifier over SSH, approved explicitly by the user) and force-killing the real process per the gotcha above. **How to apply:** after any tunnel restart, `API_PUBLIC_URL`/`CLIENT_WEB_URL`/`CLIENT_ADMIN_URL`/`CLIENT_MOBILE_URL` all need re-pointing to that run's actual hostnames (read from `D:\ENG\startbat-logs\tunnel-*.log`, never assumed) before trusting any test that touches media URLs or cross-origin admin/web calls.

**Verified this restart, real checks not just port-open**: Node API (`GET /` → real Express 404 JSON, confirms the app is actually routing, not just listening), ML/AI verification service (`GET /` → real service banner, `/api/v1/verify` is the live detection endpoint), Admin and Web (`200` locally and through their public tunnels). ### Camera fault re-scoped, same day — it's not two bad cameras, it's a shared USB hub problem

### 2026-08-06 — Start-Dev.bat actually didn't work at all; found and fixed 2 real cmd.exe parser bugs

User reported Start-Dev.bat "does nothing visible" when run — no windows, no servers, nothing reachable — directly contradicting the prior session's claim that its constituent commands were validated (true, but the *whole script* had never actually been run end-to-end, and that gap mattered). - `Start-Dev.bat`: `echo ... (from server\node_server, with DATABASE_URL pointed at it)` inside the mysql-container-check block — meant this script has **always** stopped dead with an unconditional `pause`+`exit /b 1` immediately after "Ensuring engirent-mysql-dev container is running...", regardless of whether Docker/the container were actually fine, and **before ever reaching any of the 6 `start "..." cmd /k ...` lines**. - `Start.bat`: the same pattern, `echo ... issue(s) and re-run...` inside the final summary's `else` block.

Reproduced both in complete isolation (a minimal repro with an always-false `if` condition still ran the `pause`/`exit` inside it, proving the block boundary itself was broken, not the condition logic) before touching the real files — then fixed both by escaping the parens (`^(...^)`), matching the pattern already correctly used elsewhere in both scripts. ## 2026-09-03 (later same day) — Face verification moved off the kiosk entirely, to the phone

**Traced the real flow before touching code** (user asked directly: "what does the user do, how does the kiosk know?"). Confirmed: app-first only — every transaction starts in the app by picking a rental, never by walking up to the kiosk cold. The kiosk continuously displays its own QR (`/api/qr-token`, `KIOSK-001:{id}:{ts}:{sig}`, 90s TTL); the phone scans it (`mobile_scanner`) and emits `app:kiosk_scan`; Node forwards `kiosk:session_validate` to the kiosk room; the **kiosk itself** checks the token's signature/TTL (`validate_qr_token_internal`) — that check, not anything the phone asserts, is the one moment "a real person is at this physical kiosk right now" becomes true. **Two real bugs found while tracing this, both fixed:**
1. **No server-side session binding.** The first draft of `/kiosk/verify-face` parsed `kioskId` out of whatever token string the app sent, with no signature/expiry re-check at the Node layer — a captured token could be replayed indefinitely from anywhere to open a locker with nobody at the kiosk. Fixed with a new in-memory `kioskSessionStore.ts`: a session is opened **only** inside the `kiosk:flow_start` handler (i.e., only after the kiosk's own validation succeeded), keyed by rentalId, 120s TTL, capped at 4 failed match attempts before forcing a re-scan. `/kiosk/verify-face` now takes no `token` field at all — kioskId comes only from the session record, never from the client.
2. **`locker_id` sent to the Pi as a UUID, not an int.** The kiosk's `_cmd_open_door` does `int(data["locker_id"])`; the claim path was passing `rental.depositLockerId` (a UUID) straight through — would have thrown on the Pi and never opened the door. Fixed by including the `depositLocker` relation and using `parseInt(lockerNumber, 10)` throughout `faceVerificationService.ts`.

**Also found and fixed while rebuilding the flow honestly (not originally asked, but directly load-bearing):** the AWAITING_DEPOSIT branch of the *old* kiosk-camera flow was dead — `kiosk:face`'s handler in `index.ts` only ever advanced DEPOSITED (claim) and ACTIVE (return); a verified owner face for a deposit fell through and did nothing. Root cause: deposit/return locker assignment used to happen only in the ungated REST `/kiosk/deposit` and `/kiosk/return` handlers, never in the face-gated socket path. New design unifies all three actions to **verify first, then open** (deposit and return now assign a locker post-verification via a shared `assignLockerAndOpen()`, same shape as claim reusing the already-assigned deposit locker) — previously deposit had no face gate at all and return opened the door *before* verifying.
