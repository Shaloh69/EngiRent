# EngiRent Hub Codebase Audit → documentation.md

Paste this into Claude Code at the root of the EngiRent repo.

---

You are auditing an existing thesis project called **EngiRent Hub** — a smart kiosk system for secure student-to-student item rentals at UCLM's College of Engineering. Per its README, it combines web/mobile apps with an automated locker kiosk: QR + facial recognition for access, YOLOv8-based AI item verification, GCash escrow payments, and ESP32-driven solenoid locks.

**Important context — treat this as a stronger warning than usual:** the README describes an elaborate monorepo (`apps/mobile/`, `apps/web/`, `apps/kiosk/`, `backend/`, `ml-service/`, `hardware/raspberry-pi/`, `hardware/esp32/`, `docker/`, `tests/e2e/`, `scripts/`) with Prisma, Docker Compose, AWS S3, Xendit, GitHub Actions CI/CD, and more. **The actual top level of this repository only contains `client/` and `server/`**, plus a handful of root-level docs (`AI_SYSTEM_DOCUMENTATION.md`, `AI_SYSTEM_DOCUMENTATION.pdf`, `AI_VERIFICATION_GUIDE.md`, `EngiRent_Hub_Analysis.md`, `ITEM_CATEGORIES.md`, `analyzation.md`, `render.yaml`) and an APK file (`Engirentpre2.apk`) checked directly into the repo. That is a large gap between documented and actual structure — likely larger than a normal case of doc drift. **Do not assume any structure, feature, or piece of tech stack described in the README actually exists until you've opened the real code and confirmed it.** Treat the README as a product pitch / aspirational spec, not documentation, for the purposes of this audit.

**A separate file, `EngiRent_02_DESIGN_MANDATE.md`, already exists for the design phase that follows this audit** — it treats the app as three distinct client surfaces (Phone App, Admin Console, Kiosk) and needs to know how the real code maps onto those three. §4 below reflects that requirement. You don't need to read the design mandate to complete this audit, but keep in mind that whatever you find in `client/`/`server/` needs to be describable in those three-surface terms.

## How to work

1. Run `git ls-files` (or equivalent) for a full, real inventory before writing anything. Compare it directly against what the README claims exists — this comparison is itself a required output (see §14 below).
2. Map what `client/` and `server/` actually contain — don't assume they mirror the README's `apps/web`, `apps/mobile`, `backend/`, `ml-service/` split. They may be structured completely differently (e.g. `client/` could contain the web app, the kiosk UI, and/or the mobile app together; `server/` could contain the Node backend and/or the ML service together, or the ML service may not exist as committed code at all).
3. For every root-level doc file (`AI_SYSTEM_DOCUMENTATION.md`, `AI_VERIFICATION_GUIDE.md`, `EngiRent_Hub_Analysis.md`, `ITEM_CATEGORIES.md`, `analyzation.md`), read it, but verify every claim in it against real code the same way you verify README claims — these may be equally aspirational, equally stale, or genuinely authoritative; determine which per-document, don't assume.
4. Check whether `Engirentpre2.apk` being committed directly to the repo is intentional (a release artifact) or accidental bloat — note its size and whether `.gitignore` should be excluding build artifacts like this.
5. Check `render.yaml` and trace what's actually configured for Render deployment — which services, what they map to in `client`/`server`.
6. If ML/AI verification (YOLOv8), facial recognition, GCash payment integration, ESP32/hardware communication, or any other README-claimed feature doesn't appear anywhere in the actual code, say so plainly — "claimed in README, no implementation found" is a valid and expected finding here, not a failure of your search.
7. Note current git branch, last several commits, and any obvious half-finished work (commented-out code, TODO/FIXME, stubbed routes, functions that raise "not implemented").

## Sections `documentation.md` must contain

1. **System overview** — plain-language paragraph describing what the system *actually does* based on real code, not the README's pitch. If large parts of the README's vision aren't implemented, say so here up front rather than burying it.
2. **Architecture diagram (mermaid or ASCII)** — only the components that actually exist in code, with real protocols/ports where determinable.
3. **Real repo structure** — `client/` and `server/` (and anything else actually present) broken down to a reasonable depth, one line per major folder on its responsibility. Explicitly note this replaces the README's claimed structure.
4. **Client breakdown** — tech stack (from actual `package.json`/`pubspec.yaml`, not the README's table), what's inside `client/` (web app? kiosk UI? mobile app? some combination?), page/route or screen inventory, component inventory, state management approach, styling/design system in use (or lack of one). **Explicitly map what's found onto three distinct surfaces — Phone App, Admin Console, and Kiosk UI — even if they currently live in the same folder or aren't cleanly separated in the code.** This mapping is required input for the design phase that follows this audit; if the three surfaces aren't cleanly separable in the current code, say so explicitly rather than forcing an artificial split.
5. **Server breakdown** — tech stack (from actual `package.json`/`requirements.txt`), what's inside `server/` (Node API? ML service? both? something else?), entry point(s), folder structure, key modules.
6. **API surface** — every real route/endpoint found in code: method, path, purpose, auth requirement, request/response shape. Compare against the README's claimed endpoint list (`/api/auth/register`, `/api/rentals`, `/api/kiosk/deposit`, `/api/ml/verify`, etc.) and flag any that don't actually exist, and any real ones the README doesn't mention.
7. **Database schema** — actual tables/columns/relationships from real schema/migration files (Prisma schema, raw SQL, or whatever's actually used) — not the README's claimed `users`/`items`/`rentals`/`transactions`/`lockers`/`verifications` table list until confirmed against real files.
8. **AI/ML verification** — is there actually a YOLOv8 (or any) model integration in the committed code? If yes: model location, classes, confidence threshold, how it's invoked. If no: say so clearly, this is a likely gap given the structural mismatch already found.
9. **Hardware/IoT integration — full inventory, not just presence/absence.** Is there actual Raspberry Pi / ESP32 / GPIO / MQTT code committed anywhere, or is this entirely described in docs with no implementation? Check thoroughly since `hardware/` isn't in the real top-level structure at all. If any hardware code exists, produce a concrete inventory: every physical component referenced in code or config (Pi model, ESP32 boards, camera(s), QR scanner, touchscreen, solenoid locks, stepper motor, sensors) — not just "hardware exists," but what specifically, and whether it's real working code or placeholder/example code copied from a tutorial.
10. **End-to-end process flow — walk every user journey as actually coded, step by step.** This is separate from the API list in §6 — it's the sequence of what happens, not just what endpoints exist. Trace at minimum: (a) an owner listing an item, (b) a renter requesting and paying for a rental, (c) depositing an item at the kiosk (QR/face auth → locker assignment → AI verification → confirmation), (d) claiming a rented item from the kiosk, (e) returning an item (condition check, late fee calculation if any). For each step, state plainly whether the flow is fully implemented end-to-end in code, partially wired, or purely conceptual (described in docs, no corresponding code path found). Diagram at least one full flow (mermaid sequence diagram is fine) using only what's actually implemented — don't fill in gaps with the README's intended behavior.
11. **Payment integration** — is GCash/Xendit integration real code or aspirational? Check for actual API calls, webhook handlers, or escrow logic versus just env var placeholders.
12. **Auth & permissions** — how user vs. owner vs. admin access is actually enforced, session/token mechanism, anywhere it's inconsistently applied.
13. **Config & environment** — every env var actually read by the code, grouped by service, what it controls.
14. **Deployment** — what `render.yaml` actually configures, and whether it matches what `client`/`server` actually need to run.
15. **README/docs drift log** — the single most important section given the scale of the mismatch found. A specific, itemized list: for every major feature/folder/technology the README claims, state whether it was found in real code, partially found, or not found at all. Do the same for each of the other root-level `.md` docs (`AI_SYSTEM_DOCUMENTATION.md`, `AI_VERIFICATION_GUIDE.md`, `EngiRent_Hub_Analysis.md`, `ITEM_CATEGORIES.md`, `analyzation.md`) — note which ones turned out to be accurate/useful references versus which are stale or aspirational.
16. **Feature completeness matrix** — table: Feature | Status (Done / Partial / Stubbed / Not started / Not found in code at all) | Evidence (file path, or "none found" if applicable). Cover at minimum: user auth, item listing/browsing, rental request/approval flow, GCash payment, QR-code kiosk interaction, facial recognition, AI item verification, locker/solenoid control, conveyor system, notifications, admin dashboard, mobile app.
17. **Known issues / rough edges** — error handling gaps, hardcoded values, security concerns (hardcoded secrets, missing auth checks), the committed APK, anything else notable.
18. **Open threads** — anything with evidence of being mid-flight (recent WIP commits, half-written functions).

## Ground rules

- Every non-trivial claim traceable to a file path (line numbers where useful).
- Descriptive only — no recommendations or "should build next" in this pass, that comes later.
- Given how far the README strays from the real top-level structure, apply extra scrutiny rather than assuming any individual README claim is accurate just because some others turn out to be true.
- If a section has nothing implemented, say so plainly ("Not implemented — no code found") rather than skipping it or padding it with the README's description.
- Write `documentation.md` at the repo root. Prefer tables/bullets over prose paragraphs wherever the info is structured.

Begin with the full file inventory and the README-vs-reality structural comparison, then work through the sections above.
